# Product Constraints

Жёсткие продуктовые ограничения — правила, которые UI и API обязаны
соблюдать всегда. Каждый констрейнт: формулировка → почему → где
enforced. При изменении поведения сверяйтесь с этим списком; новые
ограничения добавляются сюда же. Более широкий каталог доменных правил —
[edge-cases.md](edge-cases.md).

## C1. Расчёт теста не считает по несохранённым правкам

**Правило.** Расчёт доступен, пока форма отработки совпадает со своим
исходным состоянием. Как только в неё внесли правки (закладка, выход,
причины), расчёт блокируется, а прежний результат скрывается: нужно либо
**сохранить**, либо **отменить** правки (кнопка «Отменить» возвращает
редактор к исходному состоянию).

Для **новой партии** листа ещё нет, исходное состояние формы — закладка =
выход = заказ, поэтому расчёт доступен сразу и отвечает на вопрос «сколько
теста нужно по заявкам».

**Почему.** Расчёт выполняется бэкендом по **сохранённым** данным
(read-time декоратор накладывает журнал на заказы). Если считать при
несохранённых правках, пекарь получит цифры, не совпадающие с тем, что
видит в редакторе, — тихое расхождение опаснее лишнего клика.

Пока правок нет, расхождения быть не может: у новой партии на экране стоят
количества по заявкам, и расчёт берёт их же. Требовать сохранённый факт до
расчёта означало бы переворачивать работу с ног на голову — тесто ставят
**до** выпечки, а не после, и знать его объём нужно заранее.

**Где enforced.**
- `frontend/internal/web/static/app.js` (`initializeProduction`) — сравнивает
  текущую форму с исходным снимком, блокирует кнопку расчёта и показывает
  подсказку;
- `frontend/internal/web/templates/components/monitor.html` — панель расчёта с
  флагом `Dirty` подключает эту защиту; страницы новой партии и сохранённого
  листа используют одну и ту же панель;
- `frontend/internal/web/production.go` — после сохранения делает канонический
  redirect на сохранённый лист, поэтому расчёт всегда читает факт из API.

Бэкенд-инвариант не требуется: API и так считает только по сохранённым
данным — констрейнт защищает пользователя от рассинхрона на экране.

## C2. Тесто разных типов заявок не суммируется

**Правило.** Выбор заказов для партии/расчёта ограничен одним типом
заявки; batch-мониторинг отклоняет смешанные типы.

**Почему.** У каждого типа свои коды теста; сумма по разным наборам кодов
бессмысленна.

**Где enforced.** UI выбора (`initializeSelection` в
`frontend/internal/web/static/app.js`), backend
`GET /monitor/batch` (400 на смешанные типы).

## C3. Отработка не изменяет заказ

**Правило.** Журнал отработок — единственное место хранения факта; заявка
и строки заказа не мутируются, `produced_*` в ответах — read-time
декорация.

**Почему/где.** См. [edge-cases.md](edge-cases.md#production-sheets-отработка)
и `docs/services/order.md`.

## C4. Соединение с RabbitMQ переживает обрыв

**Правило.** Publisher и consumer берут канал через `rabbitmq.Conn`, а не
держат `*amqp.Connection`. `Conn` пересоединяется, когда закэшированное
соединение закрыто.

**Почему.** `amqp091-go` не переподключается сам. После обрыва — рестарт
брокера, failover, idle reap — любой `Channel()` на старом соединении
возвращает `504 "channel/connection is not open"` до конца жизни процесса.
Одно соединение, взятое при старте, превращает временный сбой в
постоянный: релей outbox бесконечно ретраил раз в 2 секунды по мёртвому
соединению и не сливал очередь.

**Где enforced.** `pkg/rabbitmq/client.go` (`Conn.Channel`), тест
`TestConnRecoversFromADroppedConnection` (нужен брокер,
`RABBITMQ_TEST_URL`).

**Известное ограничение.** Бот при обрыве канала возвращает ошибку из
`StartConsumer`, errgroup валит процесс, и потребитель восстанавливается
только перезапуском. Соединение теперь переподключается, но цикла
перезапуска потребителя внутри процесса нет.

**Postgres устроен иначе — не чините его так же.** `pgxpool` уже
переподключается сам: выбрасывает битые соединения, набирает новые по
требованию и подчищает мёртвые раз в `HealthCheckPeriod`. Слой
переподключения поверх пула был бы дублированием. Единственное, чего пул
не умеет, — возникнуть раньше, чем база начнёт принимать соединения,
поэтому в `OpenPostgres` есть ограниченный ретрай **только на старте**
(1+2+4+8+16 с, шесть попыток, с уважением к отмене контекста).
