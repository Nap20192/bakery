# Bakery — Agent Instructions

Telegram-first ordering system for a bakery: shops place orders to the workshop,
bakers see all orders and ingredient calculations, admins manage users and the
iiko ERP sync. Two surfaces — a Telegram bot and a Telegram Mini App / web
frontend — talk to the same backend.

This document describes the architecture and how to maintain and extend it.
Keep it in sync when you change structure.

Detailed reference lives in **`docs/`** (see `docs/README.md`):
architecture, per-service pages, every DB query, the HTTP contract
(`docs/api/openapi.yaml`), the UI kit, commands, feature workflow, and the
edge-case catalog. This file is the working summary; `docs/` is the deep dive.

---

## 1. Big picture

The codebase is a **modular monolith** organized as independent services, each
following **clean architecture** with **dependency inversion**. The layout
mirrors the `thangchung/go-coffeeshop` counter service, adapted to a monolith
with shared transport.

- One Go module: `bakery` (Go 1.26).
- Persistence: PostgreSQL via `pgx/v5`, queries generated by `sqlc`.
- Async: RabbitMQ (order events → bot) through a **transactional outbox**.
- Two binaries: `cmd/worker` (HTTP API + sync + cleanup + outbox relay) and
  `cmd/bot` (Telegram bot + order-event consumer).
- Frontend: React 19 / Vite / Tailwind 4 Mini App (web + Telegram), typed
  against the OpenAPI contract.

### Dependency direction (inward only)

```
delivery (infra/http, inbound/bot)  ─┐
infra/repo (adapters)               ─┤──►  usecase (ports + service)  ──►  domain
composition (app/, deps)            ─┘
```

The **usecase** layer declares the interfaces it needs (`UseCase`,
`Repository`, …) and never imports infrastructure. Adapters (`infra/repo`,
`infra/http`) depend on the usecase; the composition root wires them. The
**domain** is pure: no DB, pgx, sqlc, HTTP, telebot, or other services.

### API contract

`docs/api/openapi.yaml` is the single source of truth for the HTTP API:

- backend: `internal/inbound/api/openapi_test.go` fails when registered
  routes and the spec diverge (both directions);
- frontend: `make api-gen` regenerates `frontend/src/api/schema.d.ts`
  (openapi-typescript) and typechecks the `openapi-fetch` client.

Any route/DTO change ⇒ update the spec ⇒ `go test ./internal/inbound/api` ⇒
`make api-gen`. See `docs/adding-features.md` for the full loop.

## 3. Anatomy of a service

Every service lives under `internal/services/<svc>/` with this internal layout:

```
internal/services/order/
  domain/               pure business logic + entities + domain events (no infra imports)
  usecase/order/        UseCase + Repository ports, DTOs, service impl
  infra/repo/           Repository adapter over sqlc
  infra/http/           HTTP delivery adapter (Handler + RegisterRoutes) — where it has HTTP endpoints
  infra/outbox/         (order only) outbox relay publishing stored events
  app/                  composition root: New(...) wires usecase + repo (+ deps)
```

Not all services have every folder:

- `admin` has no `domain`/`repo` — it orchestrates `auth` + `department` via
  ports it declares; `app/` holds the adapter from those services to its ports.
- `sync` has no `domain`/`http` — it's a background loop (iiko → DB) started
  by the worker.
- `techcard` has no `http` — internal capability wired in the worker.

### Package naming

- usecase package: `<svc>uc` import alias, declared `package <svc>uc` (e.g.
  `orderuc`). The folder is `usecase/<svc>`.
- domain package: `package <svc>` under `domain/` (import alias
  `<svc>domain`, e.g. `orderdomain`).
- repo: `package <svc>repo` under `infra/repo`.
- http: `package <svc>http` under `infra/http`.
- app: `package <svc>app` under `app/`.

### Ports live with the consumer

`usecase/<svc>/interfaces.go` declares the `UseCase` (the boundary delivery
talks to) and the `Repository`/etc. ports the service depends on. The service
never references sqlc or pgx types in its signatures — repos map sqlc rows to
domain/DTO types. Don't leak `sqlc.*` past `infra/repo`.

Errors delivery can act on are `apperr` sentinels (`<svc>.<code>` + safe
Russian message); `httpx.WriteAppError` maps `Kind` → HTTP status in one place.

## 4. Composition root (`internal/deps`)

Wiring is two-phase, both using functional options:

1. **`InfraDeps`** (`deps.NewInfraDeps`): infrastructure — config, pgxpool,
   sqlc `*Queries`, RabbitMQ publisher/consumer, iiko client.
   Options: `WithConfig`, `WithPostgres`, `WithRepositories`, `WithRabbitMQ`,
   `WithIikoClient`.

2. **`AppDeps`** (`deps.NewAppDeps`): the services + transport, built from
   infra. Each `WithXService(infra)` option **delegates to that service's
   `app.New(...)`** — `deps` stays a thin orchestrator, the actual wiring lives
   in `internal/services/<svc>/app/`.

```go
func WithOrderService(infra *InfraDeps) appOption {
    return func(deps *AppDeps) error {
        deps.OrderService = orderapp.New(infra.queries, infra.DB)
        return nil
    }
}
```

Order of options matters: a service that depends on another (e.g. `admin`
needs `auth` + `department`) must be declared after its dependencies.

The two binaries select different option sets:

- **worker**: all services + `WithOrderOutboxRelay` + `WithAPIServerConfig`
  (no bot — the worker binary does not even link telebot).
- **bot**: only `WithAuthService` + `WithDepartmentService`; `cmd/bot/main.go`
  builds the `bot.OrderBot` itself and gets the consumer via
  `infra.EventConsumer()`. No API server, no admin, no iiko.

## 5. HTTP transport

Shared plumbing in `internal/inbound/api`:

- `server.go` — `Server` holds an `httpx.Authenticator` and route registrars;
  `NewServer(...)` builds each service's HTTP `Handler` and the order
  `OrderPresenter`, registers `GET /health` and each handler's
  `RegisterRoutes(mux, auth)`.
- `middleware.go` — cors, panic recover, request logger (attaches a
  correlation id that flows into outbox events and bot logs).
- `httpx/` — `WriteJSON`/`WriteError`/`WriteAppError`, `ErrorResponse`,
  `DepartmentResponse`, `Trim`, `ParseRequestDate`, `UniqueQueryValues`, the
  `MiniAppUser` viewer + context accessors, and the `Authenticator` with the
  three auth middlewares + Telegram initData validation.
- `openapi_test.go` — the spec↔routes sync test (see §1 API contract).

Per-service handlers in `internal/services/<svc>/infra/http`:

- Each is a `Handler` struct holding its `UseCase` and a
  `RegisterRoutes(mux *http.ServeMux, auth *httpx.Authenticator)` method that
  wires its routes behind the right middleware.
- `orderhttp.OrderPresenter` projects orders to API responses (resolving
  departments). It's exported and shared: `monitorhttp` embeds order responses
  in calculation results (a legitimate monitor → order dependency).

### Authentication (two surfaces, one viewer)

Every request authenticates via the `Authorization` header:

- `tma <initData>` — Telegram Mini App: HMAC-validated initData (24h max
  age), resolved by `telegram_username`.
- `Bearer <token>` — plain web: HMAC session token from `POST /login`
  (7-day TTL), resolved by `user_id`.

Three middlewares:

- `RequireMiniAppAuth` — authenticated user with a supported role
  (admin/shop/baker); the department binding is optional and attached for
  display when present.
- `RequireAuth` — any logged-in user (e.g. `GET /me`).
- `RequireAdmin` — admin role required.

Finer rules (only shop writes orders, only baker/admin writes production)
live in the handlers on top of these.

## 6. Telegram bot (`internal/inbound/bot`)

- Thematic files: `bot.go`, `routes.go`, `handler_auth.go`,
  `handler_events.go`, `middleware.go`, `render.go`, `sender.go`,
  `session.go`, `response/`.
- `/start` prompts for the user's password, binds and saves their
  `telegram_id`, then logs them in by it on later messages; replies carry an
  «open Mini App» button.
- The bot does **not** provision users or assign roles — only admin does that,
  via the web admin panel.

### Order notifications

The bot consumes order events (see §7) and notifies, for each order:

1. the order creator (DM, WebApp button),
2. all bakers (role = baker, DM),
3. the workshop group chat (`TELEGRAM_WORKSHOP_CHAT_ID`; plain URL button —
   Telegram forbids WebApp buttons in groups).

Sends are best-effort: failures are logged, never requeued. Do not auto-send
the monitor calculation after order creation — the message ends with a
copyable `/monitor ORDER_NUMBER`.

## 7. Events (RabbitMQ) — transactional outbox

Event-driven flow from the order service to the bot:

- Domain events: `order.created`, `order.updated`, `order.cancelled`,
  `order.restored`, `order.produced`, `order.production_cleared`. The `Order`
  aggregate (`order/domain`) records them via `Record*` using
  `sharedkernel.AggregateRoot`.
- The **repository persists events to `order_outbox` in the same transaction
  as the write** (with the request's correlation id); the relay
  (`order/infra/outbox`, runs in the worker) polls unpublished rows and
  publishes them — publish-then-mark ⇒ **at-least-once**, consumers must
  tolerate duplicates.
- Transport: fanout exchange `bakery.order-events`; the bot binds a durable
  queue `bakery.bot.order-events` (names in `internal/pkg/enum/rabbitmq.go`).
- Consumer (`pkg/rabbitmq/consumer`) is a worker pool with ack/nack; the bot's
  `ConsumeOrderEvents` decodes by `type` and notifies.

## 8. Domain rules (do not regress)

The full catalog with rationale is `docs/edge-cases.md`; the load-bearing
summary:

### Departments

- Types: `shop` and `workshop` (`internal/pkg/enum`).
- Default departments: `Магазин Гагарина`, `Магазин Сарыарка`,
  `Магазин Шолохова`, `Цех Пекари`.
- Orders go shop → workshop: `from_department_id` = the shop that created it,
  `to_department_id` = `Цех Пекари` (code `pekari`).

### Order categories (типы заявок)

- Dynamic dictionary `order_categories` (seeded: «Хлеб» Х/amber, «Булочки»
  Б/sky). Admin CRUD at `/admin/categories`; a category with dishes cannot be
  deleted. Colors come from the fixed palette in `orderdomain.CategoryColors`
  (mirrored in `frontend/src/lib/categories.js` and the spec enum) — no
  arbitrary hex.
- Every new order requires `category_id`; the category letter goes into the
  order number: `<магазин>.<буква типа>.<дата>.<счётчик>` («Г.Х.08.07.26.001»).
  Counters are per shop **per category** per day. Category never changes on
  edit. Legacy orders keep numbers without the letter.
- Dish catalog entries carry `category_id`; the shop picks the category first
  and sees only its dishes (uncategorized dishes stay visible everywhere).
  Worker seeds the catalog on startup from `templates/dishes.txt` → «buns» and
  `templates/bread.txt` → «bread» (`EnsureDefaultOrderTemplates`); re-seeding
  must not clobber categories assigned by the admin, missing files are skipped.
- Baker UI: matrix grouped by category, color stripe + badge on cards,
  category filter chips; multi-select is limited to one category (dough of
  different типы is never summed). The «Таблица» view (`/orders/table`)
  splits by category the same way.
- Dough codes for the monitor calculation live on the category
  (`monitor_codes`), edited in the admin panel. A category without codes is
  a 400 telling the admin to configure them. Orders without a category fall
  back to `monitoringdomain.DefaultMonitorCodes`.

### Отработка (production fact)

- Каждая отработка — **отдельный документ**, фиксирующий **партию**:
  сохранённый выбор заказов (`production_sheet_orders`, включая заказы без
  отклонений) плюс отклонения факта (`production_sheet_items`). Связь: **у
  отработки много заказов, у заказа — максимум одна отработка** —
  принадлежность определяется выбором партии; пересечение с чужим листом —
  конфликт `order.production_exists`.
- **Заказ при отработке не изменяется вообще** — журнал является единственным
  местом хранения факта, а `produced_quantity`/`produced_reason` в ответах
  API — read-time «декоратор»: репозиторий накладывает факт из журнала на
  позиции при чтении (`GetOrderProductionFacts` + `decorateProductionFacts`;
  по позиции побеждает самый свежий лист). Заказ несёт производный
  `production_sheet_id`; UI связывает заказ↔отработку в обе стороны.
- Хранятся **только отклонения** (nil = «испечено по заявке»). Лист **без
  отклонений валиден** — партия зафиксирована и живёт до явного удаления.
- Обоснование отклонения (`reason`, до 200 символов; пресеты
  «Подгорело»/«Упало»/… + свободный текст) декорирует `produced_reason` и
  попадает в уведомление бота («Багет: 10 → 8 ⚠️ — подгорело»).
- Мониторинг считает по `OrderItem.EffectiveQuantity()` — факт приоритетнее
  заявки, поэтому расчёт теста «с учётом отработки» бесплатный.
- CRUD `/production` — только baker/admin. Историю заказа отработка **не
  пишет**; события `order.produced`/`order.production_cleared` уходят в outbox
  только при реальном изменении видимого факта (`notifyProductionChanges`).
- UI: **один редактор листа** (`ProductionSheet`) при создании (страница
  выбранных заказов) и правке (журнал `/production`), рядом — «Расчёт теста»
  по партии. Детали заказа показывают колонку «Испечено» (недовоз красным,
  излишек зелёным), карточка матрицы — метку ✓/±.
- A shop user only sees/edits its own orders; a workshop user sees all but
  cannot create shop orders. Enforced in `orderhttp.UserCanReadOrder` and the
  write handlers.

### Roles

- Roles: `admin`, `shop`, `baker`. Helpers in `internal/pkg/enum` and
  `auth/domain` (`NormalizeRole`, `IsValidRole`). Authorization is enforced by
  the `httpx` middlewares plus per-handler role checks — there is no separate
  permission matrix.
- `auth` and `admin` are separate services. The worker ensures the admin user
  on startup (`EnsureAdminUser`).
- `login`, `telegram_username`, and `telegram_id` are unique.
- **Passwords are pbkdf2-hashed and cannot be displayed** — the admin panel
  offers password **reset**, never reveal. No self-registration anywhere.

### Monitor (ingredient calculation)

- Business math is pure, in `monitor/domain`; the usecase loads the tech-card
  graph from DB and calls it.
- Use `iiko_prepared_chart_items`, not `raw_json`, for prepared-chart math.
- Formulas:
  - Assembly chart: `scale = ordered_quantity / assembled_amount`,
    `child_amount = item.amount_in * scale` (uses `amount_in`).
  - Prepared chart: `child_amount = item.amount * ordered_quantity`.
- Reports also carry `components` — the ingredient's own tech card expanded
  one level (`ComposeRecipe`), scaled to the total usage; same formulas.
- Keep cycle protection and recursion-depth limits (12). Do not add caching
  unless asked.

### iiko

- Client in `internal/outbound/iiko`.
- Integration tests skip when required env vars are unset; results saved under
  `internal/outbound/iiko/testdata/results`.

## 9. How to extend

Step-by-step checklists with the full frontend loop: `docs/adding-features.md`.

### Add an endpoint to an existing service

1. Add the method to the service `UseCase` interface (`usecase/<svc>/interfaces.go`)
   and implement it in the service + `Repository` if it needs data. Update the
   `fakeRepo` in the usecase tests.
2. Add a handler method in `internal/services/<svc>/infra/http/handler.go` and
   register the route in `RegisterRoutes` behind the correct middleware.
3. Reuse `httpx` helpers for responses; do not duplicate `WriteJSON`/DTOs.
4. Describe the route in `docs/api/openapi.yaml` — the sync test
   (`internal/inbound/api/openapi_test.go`) fails when code and spec diverge —
   then run `make api-gen` to refresh `frontend/src/api/schema.d.ts`.
5. Frontend calls go through a facade in `frontend/src/api/` (one function =
   one operation); components never call `fetch` directly.

### Add a brand-new service

1. `internal/services/<svc>/domain` — entities + pure logic (+ events if it
   emits any).
2. `usecase/<svc>` — `interfaces.go` (UseCase + ports + DTOs) and the service
   impl. No infra imports.
3. `infra/repo` — implement `Repository` over sqlc.
4. `infra/http` (if it has endpoints) — `Handler` + `RegisterRoutes`.
5. `app/app.go` — `New(...)` wiring usecase + repo (+ other deps).
6. `internal/deps`: add a field to `AppDeps` and a `WithXService(infra)` option
   delegating to `<svc>app.New(...)`. Add it to the relevant binary's option
   list (respect dependency order).
7. If it has HTTP routes, add its handler to `api.NewServer` and describe them
   in the spec (the sync test picks up new `mux.Handle` patterns automatically).

### Add a domain event

1. Define the event type in `<svc>/domain` embedding `sharedkernel.Event` with
   an `Identity()`; record it on the aggregate.
2. Persist it to the outbox in the repository, in the same transaction as the
   write (`persistOutbox`).
3. Add exchange/queue names to `internal/pkg/enum/rabbitmq.go` if new.
4. Handle it on the consumer side (`internal/inbound/bot/handler_events.go`).

### Database changes

1. Edit/add SQL in `queries/`, then run `make sqlc`. Conventions (nullable
   filters, `lower(trim())` matching, full-replace updates): `docs/database.md`.
2. Add a migration `migrations/NNNNN_name.sql` (goose-style). The worker
   applies migrations on startup via `internal/pkg/dbmigrate`.
3. `DATABASE_URL` takes priority; otherwise config builds it from `POSTGRES_*`.

## 10. Conventions & commands

Full command reference (run/restart/docker/frontend workflows):
`docs/commands.md`.

### Validate after changes

```bash
make build && make vet && make test && make lint   # lint must report 0 issues
go test ./internal/inbound/api                     # spec ↔ routes sync
make api-gen                                       # after any contract change
cd frontend && npm run lint && npm run build       # frontend changes
```

After SQL changes run `make sqlc` before building.

### Style

- Match surrounding code: naming, comment density, idioms.
- Keep formulas/business math in `domain`; data loading in `infra/repo` /
  `outbound`.
- Structured logging via `pkg/logger`. Never expose raw DB/iiko errors to
  users — log the technical cause, return a safe `apperr` message.
- Use `internal/pkg/enum` for roles, department types, iiko product types,
  sync statuses, rabbitmq names. Don't hardcode their strings.
- Frontend: features compose `ui/` primitives; `ui/` never imports from
  `features/`; overlays wrap headless `radix-ui` once in `ui/` (features
  never import radix directly); category Tailwind classes stay literal.

### Environment

- `BOT_ENV=test|prod`; `TEST_BOT_TOKEN` / `PROD_BOT_TOKEN`.
- `TELEGRAM_WORKSHOP_CHAT_ID` — workshop group chat for notifications.
- `RABBITMQ_URL`, `DATABASE_URL` (or `POSTGRES_*`).
- `LOG_PRETTY=false` for deploy. On Railway use
  `DATABASE_URL=${{Postgres.DATABASE_URL}}` and configure via Variables.

### Deploy

- `deploy/Dockerfile.worker` builds `./cmd/worker`; `deploy/Dockerfile.bot`
  builds `./cmd/bot`.
- Frontend deploys on Railway as a Node proxy (`frontend/server.js`) that
  serves the build and proxies `/api/*` over the private network.

### Guardrails

- Don't overwrite unrelated uncommitted changes or delete user files
  (`.xls`, `.md`) unless asked.
- Don't do broad refactors outside the task.
- Don't reintroduce SQLite or an in-process event bus (RabbitMQ is the bus).
- Don't add roles beyond admin/shop/baker unless asked.
- Never commit `cmd/testingorders/main.go` while it carries a hardcoded DSN —
  stage with `git add -A -- . ':!cmd/testingorders/main.go'`.
- Keep build / vet / test / lint green (and the spec sync test) before
  declaring done.
