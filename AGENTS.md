# Bakery — Agent Instructions

Telegram-first ordering system for a bakery: shops place orders to the workshop,
bakers see all orders and ingredient calculations, admins manage users and the
iiko ERP sync. Two surfaces — a Telegram bot and a Telegram Mini App / web
frontend — talk to the same backend.

This document describes the architecture and how to maintain and extend it.
Keep it in sync when you change structure.

---

## 1. Big picture

The codebase is a **modular monolith** organized as independent services, each
following **clean architecture** with **dependency inversion**. The layout
mirrors the `thangchung/go-coffeeshop` counter service, adapted to a monolith
with shared transport.

- One Go module: `bakery` (Go 1.26).
- Persistence: PostgreSQL via `pgx/v5`, queries generated by `sqlc`.
- Async: RabbitMQ (events from the order service to the bot).
- Two binaries: `cmd/worker` (HTTP API + sync + cleanup) and `cmd/bot`
  (Telegram bot + order-event consumer).
- Frontend: React/Vite Mini App (web + Telegram), separate directory.

### Dependency direction (inward only)

```
delivery (infra/http, inbound/bot)  ─┐
infra/repo (adapters)               ─┤──►  usecase (ports + service)  ──►  domain
composition (app/, deps)            ─┘
```

The **usecase** layer declares the interfaces it needs (`UseCase`,
`Repository`, `EventPublisher`, …) and never imports infrastructure. Adapters
(`infra/repo`, `infra/http`) depend on the usecase; the composition root wires
them. The **domain** is pure: no DB, pgx, sqlc, HTTP, telebot, or other
services.

## 3. Anatomy of a service

Every service lives under `internal/services/<svc>/` with this internal layout:

```
internal/services/order/
  domain/               pure business logic + entities + domain events (no infra imports)
  usecase/order/        UseCase + Repository (+ EventPublisher) ports, DTOs, service impl
  infra/repo/           Repository adapter over sqlc
  infra/http/           HTTP delivery adapter (Handler + RegisterRoutes) — where it has HTTP endpoints
  app/                  composition root: New(...) wires usecase + repo (+ deps)
```

Not all services have every folder:

- `admin` has no `domain`/`repo` — it orchestrates `auth` + `department` via
  ports it declares; `app/` holds the adapter from those services to its ports.
- `sync` has no `domain`/`http` — it's a background loop (iiko → DB) started
  by the worker.
- `techcard` has no `http` — used by the bot and the monitor service only.

### Package naming

- usecase package: `<svc>uc` import alias, declared `package <svc>uc` (e.g.
  `orderuc`). The folder is `usecase/<svc>`.
- domain package: `package <svc>` under `domain/` (import alias
  `<svc>domain`, e.g. `orderdomain`).
- repo: `package <svc>repo` under `infra/repo`.
- http: `package <svc>http` under `infra/http`.
- app: `package <svc>app` under `app/`.

### Ports live with the consumer

`usecase/<svc>/interfaces.go` declares the `UseCase` (the boundary delivery
talks to) and the `Repository`/`EventPublisher`/etc. ports the service depends
on. The service never references sqlc or pgx types in its signatures — repos
map sqlc rows to domain/DTO types. Don't leak `sqlc.*` past `infra/repo`.

## 4. Composition root (`internal/deps`)

Wiring is two-phase, both using functional options:

1. **`InfraDeps`** (`deps.NewInfraDeps`): infrastructure — config, pgxpool,
   sqlc `*Queries`, RabbitMQ publisher/consumer, iiko client.
   Options: `WithConfig`, `WithPostgres`, `WithRepositories`, `WithRabbitMQ`,
   `WithIikoClient`.

2. **`AppDeps`** (`deps.NewAppDeps`): the services + transport, built from
   infra. Each `WithXService(infra)` option **delegates to that service's
   `app.New(...)`** — `deps` stays a thin orchestrator, the actual wiring lives
   in `internal/services/<svc>/app/`.

```go
func WithOrderService(infra *InfraDeps) appOption {
    return func(deps *AppDeps) error {
        deps.OrderService = orderapp.New(infra.queries, infra.DB, infra.eventPublisher)
        return nil
    }
}
```

Order of options matters: a service that depends on another (e.g. `admin`
needs `auth` + `department`; `orderbot`/`apiserver` need several) must be
declared after its dependencies.

The two binaries select different option sets:

- **worker**: all services + `WithAPIServerConfig` (no bot).
- **bot**: services the bot uses + `WithOrderBot` (no API server, no admin).

## 5. HTTP transport

Shared plumbing in `internal/inbound/api`:

- `server.go` — `Server` holds an `httpx.Authenticator` and a
  `[]routeRegistrar`. `NewServer(...)` builds each service's HTTP `Handler` and
  the order `OrderPresenter`, then `Start()` registers `GET /health` and calls
  `h.RegisterRoutes(mux, auth)` on each handler.
- `middleware.go` — cors, panic recover, request logger.
- `httpx/` — `WriteJSON`/`WriteError`, `ErrorResponse`, `DepartmentResponse`,
  `Trim`, `ParseRequestDate`, `UniqueQueryValues`, the `MiniAppUser` viewer +
  context accessors (`WithMiniAppUser`, `MiniAppUserFromContext`,
  `IsShopUser`, `IsWorkshopUser`), and the `Authenticator` with the three auth
  middlewares + Telegram initData validation.

Per-service handlers in `internal/services/<svc>/infra/http`:

- Each is a `Handler` struct holding its `UseCase` and a
  `RegisterRoutes(mux *http.ServeMux, auth *httpx.Authenticator)` method that
  wires its routes behind the right middleware.
- `orderhttp.OrderPresenter` projects orders to API responses (resolving
  departments). It's exported and shared: `monitorhttp` embeds order responses
  in calculation results, so it depends on `orderhttp` (a legitimate
  monitor → order dependency).

### Authentication (two surfaces, one viewer)

Every request authenticates via the `Authorization` header:

- `tma <initData>` — Telegram Mini App: HMAC-validated initData, resolved by
  `telegram_username`.
- `Bearer <token>` — plain web: session token from `POST /login`
  (username+password), resolved by `user_id`.

Three middlewares:

- `RequireMiniAppAuth` — authenticated **and** attached to a supported
  department (shop/workshop). Used for orders, catalog, monitor, departments.
- `RequireAuth` — any logged-in user, no department needed (e.g. `GET /me`).
- `RequireAdmin` — admin role required (user management).

## 6. Telegram bot (`internal/inbound/bot`)

- Thematic handler files, not one giant file (`handler_start.go`,
  `handler_order.go`, `handler_orders.go`, `handler_monitor.go`,
  `handler_techcard.go`, `response_builder.go`, …).
- Build all HTML/text replies through `responseBuilder` in
  `response_builder.go`.
- `/start` prompts for the user's password, binds and saves their
  `telegram_id`, then logs them in by it on later messages.
- Identity middleware resolves the user from `telegram_id`.
- The bot does **not** provision users or assign roles — only admin does that,
  via the web admin panel.

### Order notifications

The bot consumes order events (see §7) and notifies, for each order:

1. the order creator,
2. all bakers (role = baker),
3. the workshop group chat (`TELEGRAM_WORKSHOP_CHAT_ID`).

Do not auto-send the monitor calculation after order creation. End the
order-created message with a copyable command: `/monitor ORDER_NUMBER`.

## 7. Events (RabbitMQ)

Event-driven flow from the order service to the bot:

- Domain events: `order.created`, `order.updated`. The `Order` aggregate
  (`order/domain`) records them via `RecordCreated`/`RecordUpdated` using
  `sharedkernel.AggregateRoot`; the usecase pulls and publishes them after a
  successful write through its `EventPublisher` port.
- Transport: fanout exchange `bakery.order-events`; the bot binds a durable
  queue `bakery.bot.order-events` (names in `internal/pkg/enum/rabbitmq.go`).
- Publisher wraps each event in an envelope `{type, created_at, payload}`.
- Consumer (`pkg/rabbitmq/consumer`) is a worker pool with ack/nack; the bot's
  `ConsumeOrderEvents` decodes by `type` and notifies.

## 8. Domain rules (do not regress)

### Departments

- Types: `shop` and `workshop` (`internal/pkg/enum`).
- Default departments: `Магазин Гагарина`, `Магазин Сарыарка`,
  `Магазин Шолохова`, `Цех Пекари`.
- Orders go shop → workshop: `from_department_id` = the shop that created it,
  `to_department_id` = `Цех Пекари` (code `pekari`).
- A shop user only sees/edits its own orders; a workshop user sees all but
  cannot create shop orders. Enforced in `orderhttp.UserCanReadOrder` and the
  write handlers.

### RBAC

- Roles: `admin`, `shop`, `baker` (+ `sync` capability). Matrix and helpers in
  `internal/pkg/enum` and `auth/domain` (`NormalizeRole`, `IsValidRole`).
  Authorize service commands (`/techcard`, `/sync`) and admin endpoints.
- `auth` and `admin` are separate services. The worker ensures the admin user
  on startup (`EnsureAdminUser`).
- `login`, `telegram_username`, and `telegram_id` are unique.
- **Passwords are pbkdf2-hashed and cannot be displayed** — the admin panel
  offers password **reset**, never reveal. No self-registration anywhere.

### Monitor (ingredient calculation)

- Business math is pure, in `monitor/domain`; the usecase loads the tech-card
  graph from DB and calls it.
- Use `iiko_prepared_chart_items`, not `raw_json`, for prepared-chart math.
- Formulas:
  - Assembly chart: `scale = ordered_quantity / assembled_amount`,
    `child_amount = item.amount_in * scale` (uses `amount_in`).
  - Prepared chart: `child_amount = item.amount * ordered_quantity`.
- Keep cycle protection and recursion-depth limits. Do not add caching unless
  asked.

### iiko

- Client in `internal/outbound/iiko`. Product groups:
  `ListProductGroups(ProductGroupListParams)` →
  `/resto/api/v2/entities/products/group/list`.
- Integration tests skip when required env vars are unset; results saved under
  `internal/outbound/iiko/testdata/results`.

## 9. How to extend

### Add an endpoint to an existing service

1. Add the method to the service `UseCase` interface (`usecase/<svc>/interfaces.go`)
   and implement it in the service + `Repository` if it needs data.
2. Add a handler method in `internal/services/<svc>/infra/http/handler.go` and
   register the route in `RegisterRoutes` behind the correct middleware.
3. Reuse `httpx` helpers for responses; do not duplicate `WriteJSON`/DTOs.

### Add a brand-new service

1. `internal/services/<svc>/domain` — entities + pure logic (+ events if it
   emits any).
2. `usecase/<svc>` — `interfaces.go` (UseCase + ports + DTOs) and the service
   impl. No infra imports.
3. `infra/repo` — implement `Repository` over sqlc.
4. `infra/http` (if it has endpoints) — `Handler` + `RegisterRoutes`.
5. `app/app.go` — `New(...)` wiring usecase + repo (+ other deps).
6. `internal/deps`: add a field to `AppDeps` and a `WithXService(infra)` option
   delegating to `<svc>app.New(...)`. Add it to the relevant binary's option
   list (respect dependency order).
7. If it has HTTP routes, add its handler to `api.NewServer`'s `handlers`
   slice.

### Add a domain event

1. Define the event type in `<svc>/domain` embedding `sharedkernel.Event` with
   an `Identity()`; record it on the aggregate.
2. Publish it from the usecase via its `EventPublisher` port after the write.
3. Add exchange/queue names to `internal/pkg/enum/rabbitmq.go` if new.
4. Handle it on the consumer side (`internal/inbound/bot`).

### Database changes

1. Edit/add SQL in `queries/`, then run `sqlc generate`.
2. Add a migration `migrations/NNNNN_name.sql` (goose-style). The worker
   applies migrations on startup via `internal/pkg/dbmigrate`.
3. `DATABASE_URL` takes priority; otherwise config builds it from `POSTGRES_*`.

## 10. Conventions & commands

### Validate after changes

```bash
go build ./...
go vet ./...
go test ./...
golangci-lint run ./...     # must report 0 issues
```

After SQL changes also run `sqlc generate` before the above. Frontend changes:
lint + build in `frontend/`.

### Style

- Match surrounding code: naming, comment density, idioms.
- Keep formulas/business math in `domain`; data loading in `infra/repo` /
  `outbound`.
- Structured logging via `pkg/logger`. Never expose raw DB/iiko errors to
  users — log the technical cause, return a safe message.
- Use `internal/pkg/enum` for roles, permissions, department types, iiko
  product types, sync statuses, rabbitmq names. Don't hardcode their strings.

### Environment

- `BOT_ENV=test|prod`; `TEST_BOT_TOKEN` / `PROD_BOT_TOKEN`.
- `TELEGRAM_WORKSHOP_CHAT_ID` — workshop group chat for notifications.
- `RABBITMQ_URL`, `DATABASE_URL` (or `POSTGRES_*`).
- `LOG_PRETTY=false` for deploy. On Railway use
  `DATABASE_URL=${{Postgres.DATABASE_URL}}` and configure via Variables.

### Deploy

- `deploy/Dockerfile.worker` builds `./cmd/worker`; `deploy/Dockerfile.bot`
  builds `./cmd/bot`.

### Guardrails

- Don't overwrite unrelated uncommitted changes or delete user files
  (`.xls`, `.md`) unless asked.
- Don't do broad refactors outside the task.
- Don't reintroduce SQLite or an in-process event bus (RabbitMQ is the bus).
- Don't add roles beyond admin/shop/baker/sync unless asked.
- Keep build / vet / test / lint green before declaring done.
