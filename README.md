# Bakery

Telegram-first ordering system for a bakery. Shops place orders to the workshop, bakers see all orders and ingredient calculations, admins manage users and the iiko ERP sync.

Two surfaces — a **Telegram bot** and a **Telegram Mini App / web frontend** — talk to the same backend.

---

## Architecture

Modular monolith with clean architecture and dependency inversion. Each service lives under `internal/services/<svc>/` with strict layering:

```
delivery (infra/http, inbound/bot)  ─┐
infra/repo (adapters)               ─┤──►  usecase (ports + service)  ──►  domain
composition (app/, deps)            ─┘
```

**Stack**

| Layer | Technology |
|---|---|
| Language | Go 1.26 |
| Database | PostgreSQL via pgx/v5, queries generated by sqlc |
| Async | RabbitMQ (order events → bot notifications) |
| Frontend | Go `html/template` + HTMX 2.0.4 + plain CSS/JavaScript |

**Three binaries**

- `cmd/worker` — HTTP API + iiko sync + order cleanup; applies DB migrations on startup
- `cmd/bot` — Telegram bot + RabbitMQ order-event consumer
- `frontend` — HTML/HTMX BFF for the Telegram Mini App and web

## Directory layout

```
cmd/
  worker/main.go        HTTP API + sync + cleanup
  bot/main.go           Telegram bot + event consumer

internal/
  config/               env config + dotenv loader
  deps/                 composition root (InfraDeps + AppDeps)
  pkg/                  shared packages (authtoken, dbmigrate, enum, helpers, sharedkernel)
  inbound/
    api/                HTTP server + middleware (CORS, recover, logger)
    api/httpx/          shared HTTP primitives, auth middlewares
    bot/                Telegram handlers, sessions, notifications
  outbound/
    db/                 pgxpool + sqlc generated code
    iiko/               iiko ERP REST client
  services/
    order/              order domain, use cases, HTTP handlers, outbox relay
    monitor/            ingredient calculation (pure domain math)
    auth/               login, password, token, RBAC
    admin/              user management (orchestrates auth + department)
    department/         department CRUD
    techcard/           iiko tech-card graph (used by monitor + bot)
    sync/               background iiko → DB sync

pkg/
  logger/               structured slog logger
  rabbitmq/             connection, publisher, consumer worker-pool

migrations/             goose-style SQL migrations
queries/                sqlc SQL source files
templates/              seed data (dish catalog)
deploy/                 Dockerfile.worker, Dockerfile.bot
frontend/               Go HTML/HTMX Mini App
  internal/application/ CQRS Queries/Commands and ports
  internal/backend/     typed worker HTTP adapter
  internal/web/         handlers, templates, CSS and JavaScript
```

## Getting started

### Prerequisites

- Go 1.26+
- PostgreSQL
- RabbitMQ
- [sqlc](https://sqlc.dev) (for SQL codegen)
- [golangci-lint](https://golangci-lint.run) (for linting)

### Configuration

Copy `.env.example` to `.env` and fill in the values:

```bash
cp .env.example .env
```

Key variables:

| Variable | Description |
|---|---|
| `BOT_ENV` | `test` or `prod` |
| `TEST_BOT_TOKEN` / `PROD_BOT_TOKEN` | Telegram bot token |
| `MINI_APP_URL` | Public HTTPS URL of the deployed frontend |
| `TELEGRAM_WORKSHOP_CHAT_ID` | Workshop group chat for order notifications |
| `DATABASE_URL` | PostgreSQL connection string (overrides `POSTGRES_*`) |
| `RABBITMQ_URL` | RabbitMQ connection string |
| `IIKO_HOST` / `IIKO_LOGIN` / `IIKO_PASSWORD` | iiko ERP credentials |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Initial admin user (created on startup) |

### Run with Docker Compose

```bash
docker compose up
```

### Run locally

```bash
# Worker (HTTP API)
go run ./cmd/worker

# Bot (Telegram)
go run ./cmd/bot

# Frontend (HTML/HTMX on :5173)
FRONTEND_ADDR=:5173 BACKEND_URL=http://127.0.0.1:8080 go run ./frontend
```

## Authentication

The worker API authenticates via the `Authorization` header:

- `tma <initData>` — Telegram Mini App: HMAC-validated initData resolved by `telegram_username`
- `Bearer <token>` — Plain web: session token from `POST /login` (username + password)

The frontend BFF exchanges either credential for an `HttpOnly`,
`SameSite=Lax` cookie. Browsers submit HTML forms to the BFF; only the BFF
calls the worker JSON API.

---

## Events

Order events flow from the worker to the bot via RabbitMQ:

1. Order service records domain events (`order.created`, `order.updated`)
2. Usecase publishes them to fanout exchange `bakery.order-events`
3. Bot consumes queue `bakery.bot.order-events` and notifies the order creator, all bakers, and the workshop group chat

## Deploy

Dockerfiles for each binary are in `deploy/`:

```
deploy/Dockerfile.worker
deploy/Dockerfile.bot
frontend/Dockerfile
```

The worker applies DB migrations automatically on startup. Set `DATABASE_URL` and `LOG_PRETTY=false` for production.
