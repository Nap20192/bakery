# Frontend Behavior

## Назначение

Frontend используется как рабочий интерфейс для магазина, пекаря/цеха и администратора.
Интерфейс должен показывать только действия, которые нужны текущей роли.

Реализация: Go BFF рендерит HTML-шаблоны, HTMX улучшает навигацию и формы,
plain CSS/JavaScript отвечают за адаптивность и локальные взаимодействия.
Браузер не вызывает worker API напрямую.

## Технические границы

- Frontend — BFF, а не второй backend: авторизация, cookie, CSRF, HTML-роуты,
  projection во view model; бизнес-правила, сохранение, права и расчёты остаются
  в worker API.
- Все вызовы worker идут через `frontend/internal/application` Queries/Commands
  и `frontend/internal/backend`. Шаблоны и `app.js` не собирают JSON API руками.
- HTML-формы должны работать без JavaScript настолько, насколько это возможно;
  HTMX только улучшает навигацию, disabled-state, фрагменты и redirect.
- JavaScript разрешён для локального UX: Telegram initData, выбор партии,
  popups/dialog, dirty-state отработки, сортировка меню, toast, мобильная
  клавиатура, локальное масштабирование состава теста. Новые бизнес-правила в
  JS не добавлять.
- Любой frontend-facing DTO/route меняется цепочкой: OpenAPI → contract →
  backend adapter → application port → handler/view model → template.
- Мутирующие формы используют CSRF: hidden `_csrf` + `X-CSRF-Token` для HTMX/fetch.
- Ошибки API показываются безопасным русским текстом; технические причины
  остаются в логах backend/worker.

## Роли

### Shop

Магазин создает и изменяет заказы.

Доступно:
- просмотр своих заказов;
- создание заказа;
- редактирование заказа;
- профиль;
- выход в web-режиме.

Не должно быть доступно:
- расчет теста;
- выбор нескольких заказов;
- админка.

### Baker / Workshop

Пекарь и цех управляют заказами, отработками и считают тесто.

Доступно:
- сетка заказов;
- создание заказа от лица «Цех Пекари»;
- редактирование, отмена и восстановление заказов;
- фильтры по отправителю и дате выполнения;
- быстрый просмотр заказа через popup `Обзор`;
- отдельная страница просмотра заказа;
- режим выбора нескольких заказов;
- страница выбранных заказов;
- удаление заказа из текущего выбора;
- расчет теста по одному или нескольким заказам.

Не должно быть доступно:
- админка.

### Admin

Администратор управляет пользователями, справочниками и может выполнять
производственные действия как пекарь.

Доступно:
- сетка заказов и режим таблицы;
- создание, просмотр, изменение, отмена и восстановление заказов;
- режим выбора, отработки, журнал отработок и расчёт теста;
- страница пользователей;
- «Меню» — каталог блюд (по вкладкам-категориям) и типы заявок;
- просмотр тех.карт блюд по категориям;
- профиль;
- выход в web-режиме.

## Роуты

### `/session/login`

Логин/landing для web-сценария. В Telegram Mini App вход выполняется
автоматически через initData, поэтому экран нужен в основном для обычного web.

Правила:
- без основной навигации, без нижней мобильной панели и без лишнего hero-блока;
- форма центрируется в viewport на desktop и телефоне;
- поля: логин, пароль, hidden `next`; `autocomplete` включён;
- `autofocus` стоит на логине;
- ошибка входа показывается inline внутри формы;
- подпись объясняет, что в Telegram вход автоматический;
- после успешного входа сервер ведёт на `next` или рабочий экран роли;
- fallback в Mini App: автовход по initData определяет пользователя **только
  по `telegram_id`** (username изменчив и не аутентифицирует), поэтому первое
  открытие mini app до привязки id всегда показывает обычную форму
  логина/пароля; initData уходит с ней скрытым полем, и при верном пароле
  бэкенд привязывает telegram_id к учётке — следующие открытия mini app
  входят автоматически. После верного пароля сессия mini app ставится на
  сам initData (`tma`), а не на bearer-токен — каждый запрос авторизуется
  только по `telegram_id`; frontend проверяет привязку запросом `/me` и при
  неудаче показывает ошибку формы вместо bearer-сессии. Bearer-токен
  остаётся только для обычного web-входа.

### `/orders`

Основной экран заказов.

Для `shop`:
- показывает компактный список своих заказов;
- клик открывает отдельную страницу заказа;
- кнопка `Изменить` доступна пользователям с правом записи заказов.

Для `baker/workshop`:
- сверху только чипы типов заявок и кнопка `Выбор` (отправитель и дата — оси
  матрицы, отдельные фильтры не нужны);
- сетка — матрица «отправители × даты»: колонки с названиями магазинов и цеха
  (заголовки липкие — остаются под шапкой при прокрутке), горизонтальные
  полосы по дате выполнения по возрастанию (сегодня сверху, затем завтра
  и далее вперёд), внутри полосы заявки своего магазина, высоты неравномерны;
- чипы типов строятся из справочника; активен ровно один тип, а переключение
  динамически обновляет список заказов без смешивания хлеба и булочек;
- заказы грузятся окнами по 5 дней выполнения (старт: сегодня…+4);
  навигация `Раньше`/`Позже` сдвигает окно на 5 дней;
- ось дат подписана днём недели и датой без года (`Вт` / `21.07`); сегодня и
  завтра дополнительно выделены цветом полосы;
- карточка несёт только опознавательные данные: номер заказа (это же заголовок
  карточки), число позиций, автор, дата создания и состояние (отработка/отмена).
  Тип заявки показывается **только цветом** — цветная полоса слева в цвете типа
  (Хлеб, Булочки, …); буква и название типа на карточке не пишутся (тип доступен
  скринридеру через `aria-label`). Магазин на карточке не дублируется — это
  заголовок колонки. Избранное помечается звездой в углу;
- клик по карточке открывает страницу заказа; кнопка `Обзор` внутри карточки
  открывает popup быстрого просмотра;
- если заказ покрыт отработкой, чип `✓` (номер — только в `title`/`aria-label`)
  на одной строке со счётчиком позиций, в матрице и в popup — ссылка на
  `/production/N` (быстрый переход к листу отработки; в списке магазина чип
  остаётся неактивным статусом, т.к. магазин не имеет доступа к журналу);
- номер заказа всегда на своей строке над числом позиций (не в одну строку),
  поэтому колонка матрицы может быть узкой на любом экране без переноса
  номера посреди строки.

### `/orders/new`

Создание нового заказа.

Для `shop`, `baker` и `admin`.

Правила:
- страница отдельная, без панели списка заказов;
- верхняя кнопка `Закрыть` на создании не показывается: отмена уже есть в
  липкой нижней панели, дублировать действие нельзя; при редактировании
  `Закрыть` остаётся, потому что пользователь возвращается к конкретному заказу;
- у пекаря отправитель зафиксирован как «Цех Пекари»;
- первый шаг — выбор типа заявки (цветные кнопки); список блюд зависит от типа;
- при переключении типа целиком скрываются пустые группы другого типа;
- пока тип не выбран, позиции не видны; при попытке сохранить без типа форма показывает подсказку (тост) и прокручивает к выбору типа, а не молча блокирует отправку;
- тип можно сменить до сохранения; при редактировании тип зафиксирован;
- дата выполнения обязательна;
- дата по умолчанию пустая;
- рядом с полем даты — чипы быстрого выбора «Сегодня» и «Завтра»; чип
  заполняет поле, активный выделен цветом;
- нельзя выбрать дату в прошлом;
- поиск блюда не используется;
- ввод количества должен быть удобен с телефона;
- кнопки сохранения находятся внизу формы;
- когда на телефоне открыта клавиатура и фокус в поле формы, нижняя навигация
  и липкая панель сохранения скрываются, чтобы не всплывать над клавиатурой.

Черновики (только `shop`):
- кнопка «Сохранить черновик» рядом с основной кнопкой сохранения — сохраняет текущее состояние формы через `POST /orders/draft`, проходя ту же валидацию, что и создание заказа (позиции, дата, отправитель, тип);
- один черновик на пользователя на тип заявки — повторное сохранение для того же типа перезаписывает предыдущий черновик, не создавая второй;
- при успешном создании заказа черновик того же типа заявки удаляется автоматически (черновик считается «использованным»);
- черновики, которые никто не тронул долго, удаляются фоновым сборщиком мусора вместе со старыми заказами (тот же ретеншн).

### `/drafts`

Список черновиков. Для `shop` (пункт «Черновики» в основной навигации; остальным ролям — 403).

Правила:
- одна строка на черновик: бейдж типа заявки, время последнего изменения, ссылка «Загрузить» (полная перезагрузка `/orders/new?draft_category_id=N` с предзаполненной формой) и кнопка «Удалить» (`POST /orders/draft/{categoryId}/delete`);
- пустой список — заглушка с подсказкой сохранить черновик на форме создания.

### `/orders/:number`

Страница просмотра одного заказа.

Для `baker/workshop`:
- показывает детали заказа;
- доступны повтор, изменение, отмена и восстановление;
- позиции заказа сгруппированы по группам каталога с заголовками;
- рядом показывает блок расчета теста;
- кнопка `Рассчитать тесто` считает текущий заказ.

Для `shop`:
- показывает детали заказа;
- доступна кнопка `Изменить`.

### `/orders/:number/edit`

Редактирование заказа.

Для `shop`, `baker` и `admin`.

Правила такие же, как у создания:
- дата обязательна;
- дата не может быть в прошлом;
- форма должна быть удобна на телефоне.

### `/orders/selection`

Страница выбранных заказов.

Только для `baker/workshop`.

Показывает:
- раздел «Заказы партии»: выбранные заказы **в свёрнутом виде** — строка с
  номером, бейджем типа, числом позиций, автором и меткой отработки;
  клик раскрывает полные детали заказа, «✕» убирает из выбора;
- страница поделена на разделы: «Заказы партии» сверху, ниже «Отработка»
  и «Расчёт теста» (на широких экранах — двумя колонками);
- левый раздел — CSS-переключатель (без JS) «Отработка ↔ Обзор»: «Отработка»
  показывает редактируемый лист, «Обзор» — сводную таблицу партии только для
  чтения: строки — позиции (блюда), столбцы — заказы, последний столбец «Итого»
  по позиции; строка-подвал «Итого» даёт суммы по заказам и общий итог;
- кнопку удаления заказа из текущего выбора;
- расчет теста по выбранным заказам;
- панель «Отработка»: две производственные колонки «Заявка / Закладка»;
  выход (produced_quantity) больше не редактируется вручную и не
  отображается — отправляется скрытым полем, всегда равным закладке;
  закладка и выход автоматически распределяются по заявкам пропорционально
  заказу без ручного разноса; закладка по умолчанию равна заявке; при
  редактировании сохранённого листа старое значение выхода (если раньше
  отличалось от закладки) сохраняется как есть, пока закладку не тронут —
  тогда связь рвётся и значение остаётся зафиксированным; одинаковые
  позиции всех заказов показаны одной итоговой строкой, причина отклонения задаётся один раз на такую позицию и
  скрыта под кнопкой «Комментарий»; конфликт старых причин раскрывается сразу,
  потому что требует выбора одного значения;
  сохранение создаёт документ в журнале отработок — лист фиксирует всю
  партию выбранных заказов, отклонения хранятся только там, где факт
  отличается от заявки;
- расчёт теста показывает только итоги партии; кнопка «Расшифровка»
  открывает popup с полной детализацией: итоги, затем **каждый заказ
  отдельным разделом** — по каждому тесту итог, раскладка по блюдам
  (по факту отработки) и состав по техкарте;
- расчёт теста доступен **сразу**, до создания отработки: он отвечает на
  вопрос «сколько теста нужно по заявкам партии». Ждать сохранённого факта
  незачем — тесто ставят до выпечки;
- **констрейнт C1** (`docs/constraints.md`): как только в форму отработки
  внесли правки, расчёт заблокирован с подсказкой, а прежний результат скрыт;
  кнопка «Отменить» возвращает форму к исходному состоянию. То же в журнале
  отработок, где исходное состояние — последнее сохранённое.

### `/calculator`

Калькулятор теста — «черновик» пекаря. Только для `baker/workshop/admin`.

Показывает:
- переключатель типов заявок (чипы) — определяет коды теста;
- список блюд каталога активного типа с поиском и полем количества у
  каждой строки (блюда без типа видны в любом);
- кнопку «Рассчитать тесто» (активна при введённых количествах) — расчёт
  через `POST /monitor/calc` по тем же техкартам и кодам, что мониторинг
  заказов; **ничего не создаётся и не сохраняется**;
- результат — тот же блок отчётов, что у мониторинга: итог по каждому тесту,
  если у теста есть состав — итоговое количество справа является числовым
  инпутом; изменение значения локально масштабирует строки «Состав» под новый
  объём без нового запроса и без сохранения; «Расшифровка» по блюдам/заказам
  не масштабируется, потому что она объясняет исходный расчёт;
- инпут объёма хранит исходное значение с повышенной точностью в `data-*`, а
  видимые числа показываются с фиксированными тремя знаками после точки
  (0.3 → «0.300») — вес читается с точностью до грамма, нули значимы;
- раскрывающиеся «Состав» и «Расшифровка»;
- «Сбросить» очищает введённые количества и результат; смена типа
  сбрасывает устаревший результат, но не количества.

### `/orders/table`

Режим «Таблица» — сводка «блюда × даты». Только для `baker/workshop/admin`.

Показывает:
- переключатель типов заявок (чипы в цветах типов: Хлеб, Булочки, …) —
  активен один тип, таблицы меняются динамически на одной странице;
  порядок чипов — по справочнику типов, легаси-заказы без типа — чип
  «Без типа» в конце;
- строки — блюда в порядке каталога (неизвестные каталогу — в конце по
  алфавиту);
- колонки — окно дат (вчера + неделя вперёд), листается «Раньше/Позже»,
  «Сегодня» возвращает к текущему окну;
- ячейка — суммарное количество блюда (заявка + резерв) по всем заказам
  всех магазинов на эту дату; отменённые заказы не учитываются;
- отработанные клетки (каждый заказ-вкладчик покрыт листом отработки)
  **фиксируют выход**: число — фактический выход, маленькая надстрочная
  дельта «+N»/«−N» показывает отклонение от заказа (зелёная/красная);
  без отклонений — маленькая «✓». Итоги колонок считаются по выходу;
- колонки «сегодня» (зелёная) и «завтра» (янтарная) выделены цветом —
  те же цвета, что в матрице заказов;
- дата в заголовке колонки — ссылка: если все заказы колонки уже покрыты одним
  листом, она ведёт на `/production/:id`; иначе — на `/orders/selection` с
  неотработанными заказами этой даты;
- заголовок колонки подписан днём недели и датой без года (`Вт` / `21.07`);
- адаптивность под телефон: таблица живёт в скролл-контейнере с
  «заморозкой» — колонка блюд липнет влево, строка дат вверх, «Итого»
  вниз; по горизонтали двигаются только даты.

### `/production`

Журнал отработок. Только для `baker/workshop/admin`.

Показывает:
- журнал-матрицу: строки — даты создания, колонки — категории заявок
  («Хлеб», «Булочки», …), внутри ячейки — документы отработки с автором,
  числом заказов и отклонений; листы заказов без категории в журнале не
  показываются;
- таблица всегда занимает ширину экрана без горизонтальной прокрутки: колонка
  даты узкая и зафиксирована слева, колонки категорий делят остаток ширины
  поровну;
- открытие документа: тот же редактор, что при создании отработки
  (агрегированный факт по продуктам, разнос по заявкам, причины), плюс
  панель «Расчёт теста» по заказам партии — факт учитывается
  автоматически;
- удаление документа — заказы возвращаются к факту «по заявке».

### `/admin/users`

Страница управления пользователями.

Только для `admin`.

Таблица показывает логин, роль и Telegram: `@username` и, если аккаунт уже
привязан (входил через mini app или бота), Telegram ID.

### `/admin/dishes`

Каталог блюд и типы заявок. В навигации пункт называется «Меню».

Только для `admin`.

Поведение:
- вкладки по категориям (по одной на тип заявки) со счётчиком блюд; активная
  вкладка сохраняется между перезагрузками через `?tab=<id>` (по умолчанию —
  первая);
- «＋ Тип» в панели вкладок открывает попап (`<dialog>`) с формой нового типа
  заявки (название, код, буква, цвет, коды теста); после создания открывается
  вкладка нового типа;
- «⟳ Синхронизация iiko» в панели вкладок (`POST /admin/iiko/sync`, с
  подтверждением) запускает разовую синхронизацию с iiko в фоне: воркер
  дёргает `SyncOnce`, отвечает сразу (`202`), UI редиректит на вкладку с
  сообщением «Синхронизация запущена». Повторный запуск во время активной
  синхронизации возвращает `409` («уже идёт»);
- внутри вкладки, под панелью категорий:
  - «Добавить блюдо из iiko» — поиск по названию/коду; найденное добавляется
    **в текущую категорию** (тип не выбирается — он равен вкладке);
  - раскрывающийся блок «Настройки типа» — правка/удаление самой категории;
  - блюда категории сгруппированы по **группе** — заголовок группы
    со счётчиком, под ним список блюд; та же группировка, что в редакторе
    заказа. Сортировка кнопками ↑/↓ у каждой строки внутри своей группы.
    Группа — это нормализованная сущность `dish_groups` (пара категория+имя).
    Поле «Группа» в обеих формах (добавление из iiko и правка блюда) — это
    `<input name="theme" list="dish-groups-<catID>">` с `<datalist>` из
    существующих групп текущей категории: выбираешь готовую группу из списка
    **или** вводишь новую — бэкенд сам находит-или-создаёт группу по имени в
    категории (`EnsureDishGroup`), одинаковое имя переиспользует группу.
    Отдельного эндпоинта на создание группы нет — она заводится по факту
    первого блюда;
- у блюда тип заявки **обязателен**: и при добавлении, и при редактировании
  форма требует выбрать категорию (`category_id`); пустой выбор возвращает
  ошибку «Выберите тип заявки для блюда»; смена категории в форме перемещает
  блюдо в её вкладку;
- легаси-блюда без типа собираются в отдельную вкладку «Без типа» (показывается
  только если такие блюда есть; без настроек типа и без добавления), чтобы админ
  мог назначить им категорию;
- ↑/↓ переставляют строку относительно соседа внутри своей группы и сохраняют
  порядок через `POST /admin/dishes/reorder` (fetch с полным списком `codes` в
  порядке отображения); порядок в БД приводится к порядку вкладка→группа→блюдо.

### `/admin/techcards`

Тех.карты каталожных блюд, сгруппированные по типам заявок (категориям).

Только для `admin`.

Поведение:
- один раскрывающийся блок на категорию, внутри — список блюд категории;
- клик по блюду разворачивает список ингредиентов тех.карты (код, название,
  количество, единица измерения) — данные из активной техкарты iiko
  (сборочной или разложенной, что найдено первым, как в `/calculator`);
- если тех.карта не найдена или пуста, блюдо показывает причину вместо списка
  ингредиентов, а не падает всей страницей.

### `/me`

Профиль текущего пользователя.

- В web-сессии (`Bearer`) есть кнопка `Выйти` (`POST /session/logout`).
- В Mini App (сессия `tma`) кнопки `Выйти` **нет**, а `/session/logout` для
  такой сессии отвечает редиректом на `/me`, ничего не очищая: личность даёт
  сам Telegram, после «выхода» следующий запрос всё равно вошёл бы
  автоматически по initData — выход бессмыслен и только путает.

## Отработка: UI-инварианты

- В редакторе отработки видимых количественных колонок две: `Заявка` и
  `Закладка`. `produced_quantity` отправляется скрытым полем внутри ячейки
  `Закладка`, отдельной пустой колонки быть не должно.
- Табличная шапка, `colgroup`, число видимых `<td>` и `colspan` строки
  комментария должны совпадать. Если добавился hidden-input, он кладётся в
  существующую ячейку, а не в новый `<td>`.
- Кнопка `Комментарий` раскрывает поле причины для строки; конфликт старых
  причин раскрывается сразу и требует выбора одного значения.
- Dirty-state сравнивает текущую форму с исходным снимком. При отличии расчёт
  теста блокируется, прежний результат скрывается, а `Отменить правки`
  возвращает исходное состояние.

## Режим выбора заказов

Режим выбора используется только у `baker/workshop`.

Поведение:
- включается кнопкой `Выбрать заказы`; в режиме выбора остаются только
  `Отмена` и `Продолжить · N`;
- `Отмена` выходит из режима и очищает текущий выбор;
- в обычном режиме клик по карточке открывает заказ;
- в режиме выбора клик по карточке выбирает или снимает заказ; с клавиатуры —
  Enter или Пробел;
- checkbox не используется; выбранная карточка помечается рамкой и галочкой;
- выбирать можно только заявки одного типа (тесто разных типов не
  суммируется). При попытке смешать типы подсказка называет тип, который уже
  набран в партии;
- отменённые заказы и заказы, уже вошедшие в отработку, в режиме выбора
  приглушены и не выбираются. Если такой заказ был выбран **раньше**, а лист
  появился позже, он выпадает из партии сам: клиент чистит те карточки, что
  видит на экране, а `/orders/selection` отбрасывает остальные и называет их
  в сообщении. Иначе устаревший выбор дошёл бы до API и упал там на
  `order.production_exists` — уже после того, как пекарь заполнил лист;
- **выбор переживает навигацию**: перелистывание окна дат, смену фильтра типа и
  переходы между страницами. Раньше выбор молча обнулялся при любом изменении
  фильтра — это стирало набранную партию;
- кнопка `Продолжить · N` ведёт на `/orders/selection`;
- выбор хранится в `sessionStorage` и живёт до закрытия вкладки.
- страница `/orders/selection` синхронизирует storage с фактически загруженными
  заказами, поэтому вход из таблицы или старое состояние вкладки не подменяют
  текущую партию;

Роль порядка обработчиков: `hx-boost` вешает свой обработчик клика на ссылку
внутри карточки и на всплытии срабатывает раньше. Поэтому выбор слушает клик в
фазе перехвата и останавливает распространение — иначе тап уводил бы на
страницу заказа вместо выбора.

## Компонент расчёта теста

Используется на странице заказа, странице выбранных заказов, сохранённой
отработке и калькуляторе.

Поведение:
- `Рассчитать тесто` запрашивает `/fragments/monitor` или `/monitor/calc`
  через BFF, не из браузера напрямую в worker;
- ответ — список тестов. Каждый тест показывает название и итог;
- если есть `Components`, итог справа становится инпутом объёма. Пользователь
  может ввести больший или меньший объём и сразу увидеть пересчитанный состав;
- коэффициент масштабирования: `новый объём / исходный объём теста`;
- масштабируются только компоненты состава. Breakdown остаётся исходным
  объяснением расчёта;
- пустой инпут или исходное отображаемое значение возвращают состав к
  серверному результату, чтобы не пересчитать его от округлённого числа;
- при нулевом исходном объёме инпут не показывается;
- это UX-калькулятор, а не бизнес-операция: он ничего не сохраняет и не меняет
  заказ, отработку или мониторинг на backend.

Погрешности:
- backend считает с полной точностью; frontend показывает фиксированные три
  знака (0.3 → «0.300»);
- `data-base-qty` пишет число с повышенной точностью (`%.12g`), чтобы
  масштабирование не шло от округлённого текста;
- итог после локального масштабирования всё равно display-only и округляется до
  трёх знаков. Для юридически/производственно точного документа нужен серверный
  пересчёт, а не этот быстрый preview.

## Popup `Обзор`

`Обзор` должен быть внутри каждой карточки заказа.

Поведение:
- открывает popup с быстрым просмотром именно этого заказа;
- не должен менять текущий режим выбора;
- не должен выбирать заказ;
- popup закрывается кнопкой `Закрыть`.

## Навигация и мобильная клавиатура

- Desktop: навигация в шапке, текстовые пункты.
- До 900px: навигация становится фиксированной нижней tab bar с иконками и
  подписями. Контент получает нижний padding, чтобы последние элементы не
  прятались под панелью.
- При фокусе в `input`, `textarea` или `select` нижняя nav скрывается: iOS и
  Telegram WebView иначе поднимают fixed-элементы вместе с клавиатурой.
- На форме заказа вместе с nav скрывается `.editor-form .sticky-submit`, чтобы
  кнопки `Создать заказ` / `Сохранить черновик` / `Отменить` не перекрывали
  поля ввода.
- После blur элементы возвращаются без сохранения состояния в JS — это чистый
  CSS через `:has(:focus)`.

## Фильтры

Фильтры находятся сверху над сеткой.

Для `baker/workshop` доступен только фильтр по типу заявки: отправитель и
дата — оси матрицы, окно дат листается кнопками `Раньше` / `Позже`.

Для `shop` дополнительно доступны фильтры по магазину и дате выполнения.

При изменении фильтра список заказов перезагружается. Выбор партии
**не сбрасывается** — он ограничен одним типом заявки, и это уже проверяется
при каждом выборе карточки.

## Числа и даты

- Количества округляются до трёх знаков после запятой **только при выводе**
  (расчёт теста делит на сборку и даёт длинные хвосты); backend хранит и считает
  полную точность. Целые печатаются без дробной части, хвостовые нули не
  добавляются: `1.5`, не `1.500`.
  Следствие: значения меньше половины сотой показываются как `0`.
- В сетках (матрица заказов, таблица, журнал) дата выводится днём недели и
  `дд.мм` без года — год внутри видимого окна не меняется.
- Полная дата `дд.мм.гггг` остаётся там, где окно не ограничено: карточка
  заказа, страница заказа, шапка отработки.

## Empty/loading/error/success states

- Пустые списки показывают `empty-state` с конкретной подсказкой следующего
  действия, а не пустую таблицу.
- Ошибка backend в HTMX-фрагменте должна swap-иться в целевой контейнер, поэтому
  `app.js` разрешает swap для HTTP 4xx/5xx.
- Успешные мутации делают canonical redirect через `HX-Location` или обычный
  redirect; клиент не конструирует следующий экран вручную.
- Двойной submit блокируется capture-phase обработчиком до HTMX, чтобы быстрый
  double tap не создал второй заказ.
- Создание заказа дополнительно имеет короткий frontend cooldown после успеха;
  это UX-защита, не замена backend-инвариантам.
- Деструктивные действия требуют подтверждения через native `<dialog>` или
  `data-confirm`.

## Текст интерфейса

Один блок — одна подпись. Надзаголовок над заголовком допустим, только если он
не повторяет ни сам заголовок, ни пункт меню, из которого пришёл пользователь.

Описательный подзаголовок под заголовком страницы оставляется, только если несёт
правило, которое страница не показывает собой: неочевидное действие, гарантия
«ничего не сохраняется», авторство документа. Пересказ названия — не повод.

## UX/UI правила

- Один экран — одно главное действие. Terracotta/primary используется только для
  него.
- Не дублировать одинаковое действие вверху и внизу экрана: на создании заказа
  остаётся нижняя `Отменить`, верхний `Закрыть` удалён.
- Количество и номер заказа — операционные данные, им нужен mono/tabular стиль.
- Цвет категории всегда сопровождается текстом, буквой, полосой или
  `aria-label`; цвет не единственный носитель смысла.
- Для быстрых действий на телефоне целевые зоны не меньше 44px, кроме плотных
  таблиц, где это сломало бы рабочую плотность.
- Нативные элементы предпочтительнее кастома: `input type=date`, `details`,
  `dialog`, `button`, обычные формы.
- Если изменение можно сделать CSS-ом, не добавлять JS.

## Стили

Общие правила:
- рабочие поверхности белые;
- общий фон мягкий светлый;
- карточки компактные, но читаемые;
- на desktop сетка пекаря показывает до 4 карточек в ряд;
- на телефоне интерфейс должен оставаться удобным для нажатия;
- не использовать лишние кнопки;
- не дублировать действия в нескольких местах без причины.

## Вёрстка на телефоне

Проверять при **360px** — самая узкая реальная ширина. 375/390/412 дают запас.

- **Страница не должна прокручиваться по горизонтали.** Проверка:
  `documentElement.scrollWidth − clientWidth` равно нулю.
- Широкая таблица прокручивается **внутри своей обёртки**, а не растягивает
  страницу. Колонка грида, в которой лежит такая таблица, задаётся как
  `minmax(0, 1fr)`: голый `1fr` — это `minmax(auto, 1fr)`, и `min-width` таблицы
  продавливает минимум колонки, распирая весь макет вместе с соседями.
- У прокручиваемой вбок таблицы есть затемнение у правого края, пока справа
  осталось содержимое (`.scroll-frame`). Накладка лежит **поверх** скроллера:
  ячейки непрозрачны и закрывают и фон контейнера, и `box-shadow: inset`.
- Матрица, сводка и журнал ограничены по высоте видимой областью
  (`max-height` на `.matrix-scroll`/`.summary-scroll`/`.journal-scroll`) и
  прокручиваются по вертикали **внутри себя**: только так липкие шапка, ось
  и «Итого» реально остаются на экране — при безграничной обёртке вертикально
  скроллится страница и thead уезжает. На телефоне из высоты вычитается нижняя
  панель; в Mini App берётся `--tg-viewport-stable-height`, если он меньше
  `100dvh`. Липкая ось отбрасывает тень вправо (глубина вместо «обрезанных»
  цифр), а угловая ячейка thead имеет z-index выше осевых ячеек tbody — иначе
  строки наезжают на угол. В Mini App вертикальные свайпы Telegram отключены
  (`disableVerticalSwipes`), чтобы скролл таблицы не сворачивал окно.
- Таблица позиций заказа сжимается под ширину экрана вместо горизонтальной
  прокрутки: количества — то, ради чего страницу открывают, прятать их нельзя.
  Таблица отработки прокрутку сохраняет — пять колонок с полями ввода,
  включая текстовую «Причину», в ширину телефона не помещаются.

## Валидация даты

Frontend должен помогать пользователю, но backend остается главным источником правил.

Frontend:
- ставит `min` у поля даты на сегодняшний день;
- оставляет дату пустой по умолчанию при создании.

Backend:
- запрещает дату выполнения в прошлом для создания и обновления заказа.
